# Cadrage 3C, B19 : revue des candidats documentaires (version du 25 septembre 2026)

Statut : PROPOSITION, à valider avant tout code. Sources : `backlog.csv` (B19 : « Pièce, champ,
unité, localisation, version et décision consultables », dépend de B12 et B15), document 04 §4,
document 06 (« un candidat conserve valeur originale, valeur normalisée, unité, devise,
période, localisation, version du parseur et décision »), état des lieux du code du 25 septembre.

## 1. Problème

Un document de dette (échéancier, contrat, avenant, attestation d'assurance) ne produit
aujourd'hui aucun candidat persisté. L'import CSV d'échéancier remplit l'état du formulaire,
puis `lfo_save_debt_contract` réécrit `loan_schedules` en bloc, sans lien vers la pièce : on ne
peut ni revoir une ligne, ni savoir d'où elle vient, ni refaire la décision. B20 (rattacher
échéancier et assurance) et B21 (dû, payé, prévu) supposent cette provenance.

## 2. Existant réutilisable (ne pas réinventer)

| Brique | Ce qu'elle porte déjà | Limite pour B19 |
|---|---|---|
| `document_extraction_runs` / `_fields` / `_checks` (Document Intelligence, liasse) | run versionné (extracteur, spécification), valeur brute, normalisée, corrigée, unité, page, boîte, confiance, statut de revue, contrôles calculés en base | cases fiscales à code ; correction écrasée sans historique ni auteur ; version non exposée à l'écran ; aucune liste des lectures |
| Famille `AMORTIZATION_SCHEDULE` | déclarée dans la contrainte des runs | aucun extracteur |
| `parseDebtSchedule` | CSV d'échéancier, contrôles de continuité et de total | aucune persistance, aucune provenance |
| `import_record_links` | pont de provenance unique (trois formes) | aucune forme pour la dette ou l'assurance |
| Coffre `documents`, chemin navigateur → stockage privé | fichier, empreinte, billet à usage unique | page Documents sans lecture ni candidat |

## 3. Recommandation

Étendre Document Intelligence plutôt que créer un second modèle de candidats :

1. un run de famille `AMORTIZATION_SCHEDULE` par pièce d'échéancier, alimenté d'abord par le
   CSV existant (`parseDebtSchedule` devient un extracteur de run, pas un remplisseur de
   formulaire) ; le PDF reste « à transcrire » tant qu'aucun extracteur n'est livré ;
2. les lignes d'échéancier comme champs candidats localisés (numéro de ligne, colonne), avec
   valeur brute, normalisée, unité et devise ;
3. un journal immuable des décisions par champ (qui, quand, avant, après, motif), au lieu de
   l'écrasement actuel de `user_value` : même doctrine que `transaction_corrections` ;
4. la version d'extracteur et de spécification exposée et affichée ;
5. une vue de revue unique (pièce, champ, unité, localisation, version, décision), consultable
   depuis Sources et depuis la dette concernée.

Rattacher les candidats validés à `loan_schedules` (provenance, nouvelle forme de
`import_record_links`) relève de B20, pas de B19.

Alternative écartée : une table générique `document_candidates` indépendante de la liasse. Elle
dédoublerait runs, contrôles, gel et provenance déjà éprouvés, et créerait deux vérités de
revue.

## 4. Critères d'acceptation proposés

- Un CSV d'échéancier déposé crée un run consultable après rechargement, sans rien écrire dans
  `loan_schedules`.
- Chaque ligne candidate affiche valeur imprimée, valeur retenue, unité, devise, localisation,
  version de lecture et statut ; une colonne absente reste absente.
- Corriger, accepter ou rejeter une ligne laisse une trace immuable ; une seconde décision sur
  un état périmé échoue en conflit.
- Même fichier redéposé : reconnu par empreinte, aucun second run silencieux.
- Isolation par propriétaire, lecture seule pour le client, écritures par RPC `lfo_*`.
- Tests moteur, smoke transactionnel, recette navigateur locale ; rien sur la production.

## 5. Hors périmètre

Extraction PDF ou OCR ; rattachement au contrat et remplacement de l'échéancier (B20) ;
calendrier d'assurance importé (B20) ; statut dû, payé, prévu (B21).
